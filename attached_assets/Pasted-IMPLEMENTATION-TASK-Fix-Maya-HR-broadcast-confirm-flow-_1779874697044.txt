IMPLEMENTATION TASK — Fix Maya HR broadcast confirm flow + add recall.

Two problems being solved:

(1) PENDING_BROADCASTS is a module-level dict in
    routes/telegram_webhook.py:63. On Render with multiple workers or
    after a restart, the worker handling the confirm callback has an
    empty dict, so the broadcast never fans out. Row 7 in
    hr_broadcast_log was stuck at status='pending' as proof.
    Audit also revealed: zero idempotency — a double-click or
    Telegram retry can fan out twice.

(2) When a broadcast goes out wrong (typo, duplicate, wrong image),
    there is currently no way to recall it. Per-recipient message_ids
    are not stored anywhere.

Both fixes ship together. Do NOT change authorization logic. Do NOT
refactor anything outside the files listed below. Keep the diff
minimal.

=== STEP 2: broadcast_service.py ===

(a) Modify create_broadcast_log(...) to accept original_message: dict
    and store it in the new payload column via json.dumps(...) on
    insert. Keep all other columns/behavior identical. Return the
    same shape.

(b) Add a new function:

      async def claim_pending_broadcast(broadcast_id: int) -> dict | None:
          """
          Atomically transitions a broadcast from 'pending' to 'sending'.
          Returns the stored payload dict if the transition succeeded,
          None if the broadcast is already claimed, cancelled, or
          missing. This is the idempotency guard — only one caller
          wins the row.
          """

    Implementation:

      UPDATE hr_broadcast_log
         SET status = 'sending'
       WHERE id = %s
         AND status = 'pending'
      RETURNING payload

    If a row is returned, normalize payload (psycopg2 may return dict
    or string) and return it. If no row, return None.

(c) In execute_broadcast(): for every successful send response from
    sendMessage / sendPhoto / sendVideo / sendDocument / etc., capture
    response["result"]["message_id"] and insert a row into
    hr_broadcast_recipients with broadcast_id, recipient_tg_id,
    message_id, status='sent'. Batch the inserts in groups of ~50 to
    avoid 800 individual round-trips — use psycopg2 execute_values or
    SQLAlchemy bulk insert, whichever matches the existing style.
    Do NOT insert rows for 403 Forbidden responses (the bot was
    blocked) or other failures — only successful sends.

(d) Optional cleanup: if execute_broadcast() currently does its own
    UPDATE ... SET status='sending', that's now a no-op redundant
    write since claim_pending_broadcast() owns the transition.
    Remove it ONLY if nothing else depends on it; safer to leave a
    redundant write than break something.

(e) Add a new function for the recall fan-out:

      async def execute_recall(broadcast_id: int, initiated_by: int) -> dict:
          """
          Deletes all sent messages for a broadcast.
          Returns {"recalled": N, "failed": M, "expired": K}.
          'expired' = messages older than 48h (Telegram API limit).
          """

    Implementation:
      1. Atomic guard:
           UPDATE hr_broadcast_log
              SET status = 'recalling'
            WHERE id = %s
              AND status IN ('completed', 'sent')
           RETURNING sent_at, completed_at

         If no row → return {"error": "already recalled or not eligible"}.

      2. Check age. Use completed_at if present, else sent_at, else
         created_at. If now() - timestamp > 47 hours → mark status
         back to 'completed' (or whatever it was), return
         {"error": "too old", "age_hours": X}.
         Use 47h not 48h as a safety margin — by the time we finish
         iterating 800 rows we don't want to hit the wall.

      3. SELECT recipient_tg_id, message_id
           FROM hr_broadcast_recipients
          WHERE broadcast_id = %s
            AND status = 'sent'
            AND message_id IS NOT NULL

      4. For each row, call Telegram deleteMessage(chat_id, message_id).
         Rate limit to ~25 calls/sec (sleep 0.04s between calls — keeps
         well under Telegram's 30/sec global bot limit).
         On 200 OK → UPDATE recipient row SET status='recalled'.
         On error → SET status='recall_failed', log the error.

      5. UPDATE hr_broadcast_log
            SET status = 'recalled',
                completed_at = NOW()
          WHERE id = %s

      6. Return {"recalled": N, "failed": M, "expired": 0}.

(f) Add a small helper:

      async def get_broadcast_summary(broadcast_id: int) -> dict | None:
          """Returns id, status, sent_count, failed_count, content_type,
          created_at, completed_at — for the recall confirmation card."""

=== STEP 5: Handle my_chat_member updates ===

Also at the top of handle_telegram_webhook() there's a generic
"Unknown update" warning. The 'my_chat_member' update type fires when
users block/unblock the bot. Add a small handler before the unknown-
update warning:

  if "my_chat_member" in update:
      mcm = update["my_chat_member"]
      new_status = mcm.get("new_chat_member", {}).get("status")
      user_id    = mcm.get("from", {}).get("id")
      if new_status == "kicked" and user_id:
          # User blocked the bot — mark inactive so future broadcasts skip them
          await mark_user_inactive(user_id)
      elif new_status == "member" and user_id:
          await mark_user_active(user_id)
      return JSONResponse({"ok": True})

Add the two helpers in broadcast_service.py (or wherever the
hr_users updates already live):

  async def mark_user_inactive(telegram_id: int):
      UPDATE hr_users SET is_active = FALSE WHERE telegram_id = %s

  async def mark_user_active(telegram_id: int):
      UPDATE hr_users SET is_active = TRUE WHERE telegram_id = %s

This reduces the failed_count on future broadcasts (was 22 on the
last run — most of those were probably already-blocked users).

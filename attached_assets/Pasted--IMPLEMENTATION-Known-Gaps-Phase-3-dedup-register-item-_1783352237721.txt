## Step 2 — The migration (shared table)

Append ONE entry to `MIGRATIONS` in `backend/db_migrations.py`. Idempotent:

```sql
CREATE TABLE IF NOT EXISTS telegram_inbound_updates (
    bot_source   VARCHAR(32)  NOT NULL,
    update_id    BIGINT       NOT NULL,
    received_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    PRIMARY KEY (bot_source, update_id)
);
CREATE INDEX IF NOT EXISTS idx_telegram_inbound_received_at
    ON telegram_inbound_updates (received_at);
```

The `received_at` index exists so the retention delete (Step 4) is a range
scan, not a full-table scan. `bot_source` values: `'maya'`, `'alex_gradus'`,
`'alex_avtd'` (string constants, one per module).

Note: Sara keeps her own `sara_inbound_updates` — two dedup table shapes
coexist by design; the append-only rule forbids migrating Sara's. This is
documented, not a defect.

## Step 3 — Insertion points (three modules, per-module DB pattern)

The dedup LOGIC is identical everywhere (insert `(bot_source, update_id)`
with ON CONFLICT DO NOTHING; if no row inserted → duplicate → early return).

second DB pattern into a module. Do NOT write one shared helper.

## Step 4 — Retention job

In `services/scheduler.py`, add ONE daily job matching the existing
`cleanup_old_content_task` pattern (UTC CronTrigger, no timezone kwarg —
CLAUDE.md section 6). It deletes from BOTH dedup tables:

```sql
DELETE FROM telegram_inbound_updates WHERE received_at < now() - interval '48 hours';
DELETE FROM sara_inbound_updates     WHERE received_at < now() - interval '48 hours';
```

48h is generous headroom over Telegram's retry window (minutes). This folds
in the Sara-table-grows-forever gap the consult found — closing the adjacent
gap per rule 2.5. Match `scheduler.py`'s existing DB pattern (SQLAlchemy).

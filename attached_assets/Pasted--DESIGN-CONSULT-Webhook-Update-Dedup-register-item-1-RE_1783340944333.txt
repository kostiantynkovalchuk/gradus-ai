## The problem

Maya HR, Alex Gradus, and Alex AVTD webhooks have no inbound update-id
dedup (CLAUDE.md register item 1). Telegram retries any webhook that
doesn't get a fast 200 — a slow RAG call means the same update can be
processed twice: duplicate replies, duplicate side effects (broadcasts,
auth flows).

Scope boundary to keep in mind: update_id dedup solves TELEGRAM RETRIES
(same update delivered twice). It does NOT solve USER DOUBLE-TAPS
(two taps = two distinct update_ids) — that requires per-action atomic
transitions and is out of scope here unless you spot a trivially cheap
win while reading.

## Two candidate designs — validate both against the actual code

**Option A — one shared table:**
`telegram_inbound_updates(bot_source VARCHAR, update_id BIGINT,
received_at TIMESTAMP, PRIMARY KEY (bot_source, update_id))`
Composite key is mandatory: update_id is only unique PER BOT TOKEN.
One table, one cleanup job, one pattern for all future bots.

**Option B — per-bot tables (Sara's existing pattern):**
`maya_inbound_updates`, `alex_gradus_inbound_updates`,
`alex_avtd_inbound_updates`, each mirroring `sara_inbound_updates`.
Matches the table-prefix-per-product convention; three tables, three
cleanup targets, but zero cross-product coupling.

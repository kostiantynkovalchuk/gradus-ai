## Placement decision (recommended): same monorepo, second Render service

- New package `backend/sara_realtime/` — own FastAPI app, own process, own Render service. It shares the repo, the Neon DB, and the extracted Sara prompt constants, but is **never imported by `backend/main.py`** and never joins the seven-bot event loop.
- Migrations stay owned by the main backend service. The new service **must not** call `run_migrations()` — two services racing migrations on deploy is a failure mode we refuse upfront.
- One `git push origin main` deploys both services. Note: this also still restarts all seven bots — post-deploy checklist applies as always.
- Cost: one extra Render service (~$7–25/mo depending on tier). A standalone repo would save nothing and cost us duplicated prompt constants, duplicated env management, and a second deploy pipeline.

**Phase 1 scope = a talkable end-to-end service with the token-overlap optimization, instrumented for latency.** Explicitly deferred to Phase 2/3: split-brain Haiku assessment, 20-min lesson model + `sara_sessions.status='completed'` migration, wireframe UI, TG cron link, DB persistence of turns. Phase 1 keeps conversation state in memory per WebSocket session.
